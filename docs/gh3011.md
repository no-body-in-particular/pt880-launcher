# Talking to the GH3011 directly

How to reach the heart rate sensor without the vendor's app, its library, or the sensor HAL —
what works, what does not, and the several things that looked true for hours and were not.

Everything here was checked against the hardware. Where a claim rests on one observation it says
so, because most of the wrong turns below came from believing a single reading. Two claims that
an earlier version of this file stated as fact have since been disproven; they are kept at the
bottom rather than quietly deleted.

## The parts involved

    gh3011_service      a daemon, root, started by init as "gh3011_service --daemon"
    goodix_health       the kernel driver, built in, not a module
    /dev/gh_tools       its device node, crwxrwxrwx, misc 10:47
    /dev/input/event1   derived pulse and SpO2
    gh30x_sensor        the Android sensor, type 21 (heart rate)
    i2c 2-0014          the chip itself, slave address 0x14

## Starting a measurement

**Enabling `gh30x_sensor` through the sensor framework is what lights the LEDs.** Nothing else
does. From native code:

```c
ASensorManager *mgr = ASensorManager_getInstance();
int n = ASensorManager_getSensorList(mgr, &list);
/* the one with ASensor_getType() == 21; it is named "gh30x_sensor" */
ALooper *l = ALooper_prepare(ALOOPER_PREPARE_ALLOW_NON_CALLBACKS);
ASensorEventQueue *q = ASensorManager_createEventQueue(mgr, l, 3, NULL, NULL);
ASensorEventQueue_enableSensor(q, sens);
ASensorEventQueue_setEventRate(q, sens, 10000);
```

Confirmed by eye: the green LED comes on. This works from an ordinary root shell binary, so a
measurement can be triggered without the app.

Note the name. The vendor library logs `Found ppg_egc_sensor`, which is its own internal label
and matches nothing in the sensor list; searching for "ppg" finds no sensor at all.

### The driver's mode command is only a request

`_IOW('G', 9, 24)` with `{4, 0, ...}` looks like a start and is not one. `gh30x_ppgStart`, the
vendor library's exported start function, disassembles to exactly this and nothing else:

    open("/dev/gh_tools"); memset(buf, 0, 24); buf[0] = 4;
    ioctl(fd, 0x40184709, buf); close(fd);

So there is no hidden start sequence in the library to recover. Sending mode 4 by hand sets the
mode and leaves `isPPGStarted()` returning 0; the chip does not sample.

`getPPG()` is likewise not a waveform: for this chip it calls `gh30x_getreportdata` and returns
fields out of the driver's 24-byte report — the same derived pulse the input device carries.

## The driver's ioctl set, in full

Read out of the kernel image, not guessed. Everything is magic `'G'` (0x47); the driver rejects
magic `'g'` outright with EINVAL, so the Xiaomi-family drivers that use `'g'` are a different
lineage.

| command | value | what it does |
|---|---|---|
| `_IOW('G', 2, 4)` | `0x40044702` | a setting; accepts anything, and breaks `G,4` afterwards |
| `_IOWR('G', 4, 8)` | `0xc0084704` | i2c passthrough — see below |
| `_IOW('G', 7, 4)` | `0x40044707` | a setting; no visible effect on the FIFO |
| `_IOWR('G', 8, 4)` | `0xc0044708` | get current mode; returns 4 after mode 4 is set |
| `_IOW('G', 9, 24)` | `0x40184709` | mode: **4** green/PPG, **5** red/SpO2, **6** stop |
| `_IOR('G', 10, 602)` | `0x825a470a` | accelerometer FIFO |
| `_IOR('G', 11, 24)` | `0x8018470b` | derived values, about 1 Hz |

Two of these were found only after a systematic scan missed them: the scan walked `nr` 0..31
against ten round sizes, and 602 is not a round number. The size is part of the command value,
so a command whose size is not guessed is invisible.

### The accelerometer FIFO

`_IOR('G', 10, 602)` returns a count followed by that many signed triples:

    0300 | c706 8500 7ffb | c706 8500 7efb | c606 8400 7dfb | 0000...
     ^3        sample            sample            sample

It is the accelerometer, not the PPG: every triple's magnitude lands on about 2048, which is 1 g.
`(1735, 133, -1153)` is 2087; `(1093, -1593, -583)` is 2018. The kernel handler confirms the
shape — `mov r1, #600`, `movw r2, #602`, count at struct offset `0x9a`. Capacity is 100 samples.

### The 24-byte mailbox

`G,9` writes it and `G,11` reads it back — one shared buffer, not two channels. Write mode 6 and
then read the report and it returns `6 0 0 0 0 0`, which is the opcode just written, not a
measurement. Direct writes clobber whatever the daemon last put there.

While the daemon is running normally, that report reads `[?, pulse, spo2, ?, ?, worn]` and
updates at 0.7 Hz — measured over 11,860 polls at 50 Hz across a live measurement. `bph` and
`bpl` are zero throughout, which is one of several independent confirmations that the blood
pressure never comes from the driver. See vitals.md for the rest of that story.

## Tapping the daemon's own traffic

The daemon is dynamically linked (`NEEDED libc.so`), so `ioctl` is an imported symbol and can be
interposed. This is the one technique here that produced register-level truth rather than
inference:

```c
int ioctl(int fd, int req, ...)   /* must match bionic's (int, int, ...) exactly */
{
    /* real_ioctl comes from dlsym(RTLD_NEXT, "ioctl") */
    int rc = real_ioctl(fd, req, arg);
    if ((unsigned int)req == 0xc0084704u) log_the_i2c_messages(arg, rc);
    return rc;
}
```

Two things matter. Match bionic's prototype — declaring the request as `unsigned long` fails to
compile against the NDK header. And whitelist the exact commands rather than testing the magic
byte: matching every request whose second byte is 0x47 catches ioctls on unrelated fds whose
argument is not a pointer, and dereferencing those kills the daemon instantly.

Init starts the daemon with a socket it creates itself, and a hand-started copy never receives
the start request, so the tap has to go on the init-started process. A wrapper works: stop the
service (the binary cannot be replaced while it runs), copy `gh3011_service` aside to
`gh3011_service.real`, replace it with a two-line shell script that exports `LD_PRELOAD` and
execs the real binary with the original arguments, then start the service again. Restore it in
the same script so the sensor is never left wrapped.

### What the daemon actually does

Its whole conversation with the chip, at startup, is 34 transactions:

    W dd dd c0                 start
    R 0028 -> 00 31            chip id
    R 0016 -> 05 1e
    R 0008 -> 00 20
    W 0182 84db  W 0180 008d
    R 00e4 -> 00 02
    W 0064 0020  W 006a 0001  W 006a 0000  R 006c -> 00 a4
    W 0064 0022  W 006a 0001  W 006a 0000  R 006c -> 03 5d
    W 0064 0024  W 006a 0001  W 006a 0000  R 006c -> 00 7b
    R 0194 -> 00 05            W 0194 0003
    R 018a -> 08 a7            W 018a 08a4   W 018c 005d
    R 0084, 0118, 0136, 0080, 0082, 0186
    W 0020 0000  R 0022 -> 1a 80  W 0022 1a81
    W dd dd c4                 stop

Two mechanisms fall out of this, neither of which any register sweep would have found:

- **`0xdddd` is the chip's run/stop control**, written as an 8-bit value: `0xc0` starts,
  `0xc4` stops.
- **There is an indirect read**: write a selector to `0x0064`, pulse `0x006a` 1 then 0, and
  collect the result from `0x006c`. Selectors 0x20/0x22/0x24 returned 164, 861 and 123.

## The waveform: register 0xaaaa

**`0xaaaa` is the FIFO.** During a real measurement the daemon reads it over and over, and it
returns the raw photoplethysmogram:

    R aaaa 30 d9 fa 30 fd 5a 30 d9 f4 30 fd 5a 30 d9 f5 30 fd 5b 30 d9 f4 30 fd 5a ...
           \______/ \______/ \______/
            ch1      ch2      ch1

- samples are **24-bit big-endian**, three bytes each
- **two channels, interleaved** — in SpO2 mode these are the red and IR paths
- reads come back **120 or 240 bytes** at a time (40 or 80 samples)
- the sample rate works out at about **97 Hz**

### The trace is upside down

The count *falls* at systole. This is a reflective sensor, so more blood in the tissue absorbs
more light and returns less of it, and the raw FIFO value moves opposite to blood volume.

Heart rate does not care — the spacing between beats is the same whichever way up it is — so this
stayed invisible until the pulse *shape* mattered. Read as-is, the beat rises in 578 ms and falls
in 361 ms; inverted, the same beat rises in 170 ms and decays over 1012 ms. Only the second is a
pulse: arteries fill fast and drain slowly. Checked on two captures at three baseline widths, and
the as-read orientation failed all six.

Anything reading shape — upstroke time, augmentation index, and so any blood pressure estimate —
must negate first. A negative augmentation index or an upstroke longer than about 250 ms means
the sign is wrong, not that the wearer is unusual.

One 95-second measurement yielded 18,400 samples, 9,200 per channel. Detrending channel 1 with a
one-second moving average produces a textbook pulse — sharp systolic upstroke, peak, decay — and
peak-picking a clean 15-second window gives 13 beats, a median interval of 1250 ms, and **48 bpm
against the 51 bpm the device itself reported**. That agreement is the proof the decode is right.

The AC amplitude is small: about 65 counts riding on a DC level of 3,194,000, which is roughly
20 ppm. Long stretches of a real measurement also contain excursions of ±8000 counts from motion,
so any analysis has to select quiet windows rather than run over the whole capture.

### It only works on the wrist, and only once per boot

Two conditions gate every capture, and both produced long stretches of false negatives here:

- **On the wrist.** Off-wrist the LED still lights, but no measurement begins: zero events on
  `/dev/input/event1` and the daemon does no i2c at all — its log stays at exactly the 694-byte
  startup probe. An empty capture means "nothing measured", not "nothing to capture".
- **Once per boot.** After a measurement completes, the next trigger produces nothing: the daemon
  answers `GH30x_CMD_Handler 0x0006` (stop) with `gh30x_irq_status:6, type:INT_STATUS_INVALID`,
  and eventually stops logging at all. A reboot clears it. This is the same stall that prompted
  this whole investigation.

So the working procedure is: reboot, then capture immediately. `tools/gh3011/wristcap.sh` does the
capture in one command.

Also settled by these captures: the sensor HAL never opens `/dev/gh_tools` — the only holders
during a measurement are the daemon, the app, and whatever tool is running. And there is no debug
interface; `/sys/bus/i2c/devices/2-0014/` carries only the stock attributes and the driver
registers nothing beyond the misc node at `/sys/class/misc/gh_tools`. Neither matters now that
the FIFO is readable, but both were dead ends worth not re-walking.

## Reading registers ourselves: wake the chip first

Everything below this heading was written when our own reads returned zeros, and the cause turned
out to be one missing call:

**`ioctl(fd, _IOW('G',2,4), 1)` powers the chip, and the 1 is an immediate value, not a pointer.**

| | `0x0028` |
|---|---|
| daemon stopped, no power call | `0000` |
| daemon stopped, after the power call alone | `0031` — stable across reads |

The power call by itself is enough to make the part answer; `0xdddd = 0xc0` is the wake that
belongs to the start sequence below, not the thing that grants register access. An earlier
version of this file credited the wake, because that test ran seconds after stopping the daemon,
while the rail was still up from its session.

This took a long time to find, for a self-inflicted reason worth recording: logging that command
in the interposer meant dereferencing its argument as a pointer, which segfaults on an immediate
and crash-looped the daemon — so it was dropped from the tap's whitelist, taking the one call
that mattered with it. A crash-looping daemon shows up in the log as repeated
`OPEN /dev/gh_tools` lines and nothing else.

With power applied and the daemon fully stopped:

    self-drive: power rc=0
    self-drive: chip id 0031 ver 051e status 0020

That is the same `0x0031` the daemon reads, obtained from our own process with the daemon
stopped. So userspace register access does work; the earlier conclusion that it does not was
wrong, and so was the 48-register configuration table as a starting point — the daemon does not
write that table at runtime at all. Its actual start, transcribed from its traffic, is about
twenty registers:

    W dddd c0                        wake
    R 0028, 0016, 0008               id, version, status
    W 0182 84db   W 0180 008d
    R 00e4
    W 0064 <sel>  W 006a 0001  W 006a 0000  R 006c      three times, sel = 0x20/0x22/0x24
    R 0194 -> 0005   W 0194 0003
    R 018a -> 08a7   W 018a 08a4   W 018c 005d
    R 0084, 0118, 0136, 0080, 0082, 0186
    W 0020 0000
    R 0022 -> 1a80   W 0022 1a81     sets bit 0: this is what starts sampling
    W dddd a1                        arms the sample stream

and the FIFO is then drained with the preamble described above (`0xdddd = 0xc3`, status `0x0008`,
level `0x004a`, burst `0xaaaa`). `tools/gh3011/ppg.c` implements this as `-self`.

**It is not enough to start sampling.** Replaying that sequence with the daemon stopped leaves
the chip awake and answering but idle: status stays `0x0000`, the FIFO level stays 0, and every
read comes back empty. Setting bit 0 of `0x0022` does nothing because it is already set; driving
the transition instead — clear, then set — makes the register read back as `0x0000`, so the write
is being rejected or the part falls straight back to sleep.

What the daemon does beyond these writes is not visible in an i2c log: the Goodix library it
links keeps its own state machine, and the chip is interrupt-driven (`gh30x_int_msg_handler` in
the daemon's logging). Replacing it means reimplementing that, not replaying a register script.

So, as it stands:

- **reading** the chip, including the raw waveform, does not need the daemon
- **starting** a measurement does

Which is a perfectly workable division: let the daemon run the chip, and compute the vitals
ourselves from the waveform. `tools/gh3011/vitals.py` does exactly that.

## What did not work, and why (superseded in part by the above)

The passthrough's argument layout is the standard rdwr pair, and each message is the standard
12-byte `i2c_msg`:

```c
struct msg  { unsigned short addr, flags, len; unsigned char *buf; };  /* buf at offset 8 */
struct rdwr { struct msg *msgs; int n; };
```

Calling it with a null pointer and zero messages returns success and no data, which is what made
it look like a broken register interface for hours.

But the reads are not trustworthy. With the daemon stopped, reading `0x0028` — the chip id the
daemon reads as `0x0031` in the transcript above — returns zero, both before and after powering
the rail with mode 4, writing all 48 configuration registers, and sending the `0xdddd` start.
And while the daemon is running, a sweep of 0x0000-0x0700 returns whole contiguous blocks holding
one identical value per pass (0x8200 across hundreds of consecutive registers, then 0xba98),
which is bus noise rather than a register map.

So the honest position is that we cannot currently read this chip's registers from userspace, and
any conclusion previously drawn from those reads is suspect.

## The chip samples with no vendor daemon — what it took

Replaying a hand-picked subset of the daemon's writes never worked. A literal diff against a
capture that produced a real measurement showed why: **the daemon makes 129 writes before its
first burst, and we were making 32.** The missing 97 are the whole 48-register configuration
table, the calibration loop (`0x0064` select, `0x006a` pulse, `0x006c` result, three times) and
`0x0020`/`0x0022`.

An earlier section of this file said the daemon "does not write that table at runtime". That was
wrong, and it was concluded from a test run against an unpowered chip.

Replaying all 242 operations in order — reads included, generated from the capture rather than
hand-copied — starts the sensor with `gh3011_service` stopped:

      7 status=0002 level=248     <- 0x0002 is the daemon's own running status
      8 status=0002 level=228
      9 status=0004 level=260

The FIFO fills continuously and the values move (3208500 → 3208372 over a few seconds) rather
than returning the single latched constant every earlier attempt saw. `tools/gh3011/replay.c`
does this, with `seq.h` generated from a capture.

### Reading it: wait for the interrupt, then drain exactly the level

The read loop must be interrupt-driven. Polling the FIFO at arbitrary moments catches it
part-filled and re-reads entries: 74% of samples came back as consecutive duplicates, and the
apparent rate ran to 346 Hz, three times the truth.

    W dddd c3                          arm
    ioctl(_IO('G',1))                  blocks until the FIFO hits its watermark
    R 0008                             status, 0x0002 while running
    R 004a                             level - always exactly 200 once this is right
    R aaaa x N                         drain exactly level*3 bytes, 240 at a time

With the wait in place the level reads a steady 200 every round, no wait ever times out, and
duplicates fall from 74% to 8%. The watermark is the value written to `0x0044` during the start,
so the interrupt fires on a known quantity rather than whenever a poll happens to land.

Two things that are easy to get wrong here:

- **Drain the whole level, not one buffer.** A read returns at most 240 bytes = 80 samples while
  the level is 200, so a single read per burst throws two thirds away and leaves gaps that
  scatter the beat intervals across windows.
- **Measure the sample rate, do not assume it.** The loop is paced by the interrupt, so its rate
  is a property of the chip, not of any sleep in the code. Timed over 40 seconds it is **103 Hz**.
  An assumed rate scales the heart rate that comes out of the waveform in direct proportion.

### It works

    4000 sample pairs in 40.8 s = 103 Hz
    -> 61 bpm, three windows agreeing exactly, against a wearer counting 65-70

That is the sensor started, configured, and read entirely by our own code, with
`gh3011_service` stopped. `tools/gh3011/replay.c` is the working implementation.

Note that peak-picking fails on captures with movement in them where autocorrelation succeeds -
the wearer was walking around for this one. Both are worth running; disagreement between them is
a reliable sign the window is too noisy to trust.

## Measured against the vendor, same wrist, same minute

    vendor daemon:  hr=60 spo2=95   and on a second run  hr=59 spo2=99
    ours:           hr=52

So the standalone path reads about 13% low. Not noise - it repeats.

The correlation curve says why, and it is not a subharmonic or a filtering artefact. It is a
single broad hump: rising through lag 0.97 s (62 bpm), peaking at 1.09-1.11 s (54-55 bpm), then
falling. The vendor's 60 bpm sits on the rising flank at +0.09 where our peak is +0.14. Plain
autocorrelation on a pulse of a few tens of counts simply cannot localise a peak that broad.

### The mode is an ioctl, not a register

The SpO2 and heart-rate start sequences are **byte-identical** - 242 operations, not one
differing write. What selects one LED or two is `_IOW('G',9,24)`: mode 4 is green only, mode 5
drives red and IR. `seq_spo2.h` is generated from an SpO2-mode capture and is kept only to record
that it matches `seq.h` exactly.

This matters for SpO2, which needs both channels pulsatile. In the vendor's own SpO2 measurement
both move by about 70 counts a second. In ours the second channel is flat at 5 counts, so a ratio
of ratios cannot be computed from it.

### The channels start saturated, not dark

This is the part worth knowing. At the gain the start sequence applies, both channels sit railed
near a DC of 3,210,580 and read almost flat - two or three counts of movement. That looks exactly
like too little gain, and responding by raising it drives them further into the rail.

The vendor's AGC does the opposite. It *lowers* the gain, `9055 -> 4f3c -> 4645`, the DC falls to
about 3,194,400, and the pulse appears - the second channel going from 3 counts to 68 within one
burst of the change. Watching its capture read by read:

    read 0-2:  ch2 amplitude 2-3     DC 3,210,583   railed
    read 3:    ch2 amplitude 9563    DC 3,201,264   the gain change lands mid-burst
    read 4+:   ch2 amplitude 20-70   DC 3,194,400   live

So saturation must be judged by the DC level. Amplitude cannot tell a dark channel from a clipped
one - both read flat.

Two further things fall out of implementing it:

- **The settling period is unusable and must be dropped, not filtered.** Each gain step moves the
  DC by about 9500 counts, two orders of magnitude more than the pulse. Analysing across the
  transient put the rate estimate at the edge of its search range (146 bpm).
- **Bracketing the vendor's operating point does not work.** A deadband narrow enough to hold
  3,194,400 is narrower than one gain step, so the loop oscillates and the usable window collapsed
  from 3400 samples to 1200. Backing out of saturation and then stopping is stable, settling about
  33,000 counts lower than the daemon does.

None of it closes the gap: the reading stays at 49 against a vendor reference of 60.

### 0x0118 is one 16-bit gain, and getting that right woke the second channel

The daemon writes it six bytes at a time - `W 01 18 4f 3c 00 00` is `0x0118=0x4f3c` together with
`0x011a=0x0000` - and the configuration table lists the two as separate registers. Treating the
halves as independent per-channel gains produced values like `0x8419`, nowhere on the daemon's
path, and left the second channel railed:

    two 8-bit gains:   ch2 dc 3,210,567 (railed)   ac 3
    one 16-bit gain:   ch2 dc 3,197,721            ac 154

The second figure is within 3,000 counts of where the daemon operates, and it is the first time
both channels have carried a pulse under our own control - the precondition for any SpO2 at all.

It does not finish the job. One gain moves both channels together, and they are now unbalanced
the other way: ch1 has fallen to 14 counts against ch2's 154, so R comes out at 0.095 where a
real ratio of ratios runs about 0.4 to 1.0. Balancing them needs per-channel LED current, most
likely the three registers at `0x011c`, `0x011e` and `0x0120` that the configuration table sets
to `0x01ff`.

### Two dead ends, and where the gap is not

**`0x011c`, `0x011e` and `0x0120` are not per-channel LED current.** The configuration table sets
all three to `0x01ff`, which looks exactly like one current per LED. Walking each through
`0x00c0`, `0x01ff` and `0x03ff` moves the DC of either channel by under ten counts - nothing.
`tools/gh3011/ledsweep.c` does the sweep.

**Our register state already matches the daemon's.** Dumping the 57 registers it reads during a
working SpO2 run and comparing against ours after our own start, six differ and five of those are
expected: status `0x0008` and FIFO level `0x004a` depend on when they are sampled, `0x0016` is
transient, and `0x0118`/`0x0122` are the gain we deliberately set. The only real difference is
`0x0100`, reading `ea60` where the daemon has `f530`.

So the configuration is not where the remaining gap lives. What is left is what the daemon *does*
with the samples, and that is the one thing not recoverable: it is stripped, exports three
symbols - all `getopt` - and has no symbol table.

One further observation for whoever picks this up: the two channels are anti-correlated under the
single shared gain. Lower it until the second channel leaves the rail and the first falls to
3,149,775; raise it until the first is in range and the second rails at 3,210,593. The daemon
holds both together at about 3,194,500, which one 16-bit gain cannot do - so it must have a
per-channel control we have not found, and it is not the three registers above.

### The daemon runs gain control we cannot reproduce

After every burst the daemon reads the applied gain back from `0x0122` and writes a new one to
`0x0118`, six bytes at a time so `0x011a` goes with it. Across one measurement it walks
`9055 -> 2828 -> 9055 -> 4f3c -> 4645`. The two bytes behave like one LED current per channel.

Our replay pins the gain at whatever the start sequence applied and never adjusts it, which fits
both symptoms: a weak, biased pulse, and a second channel sitting at 5 counts where the vendor's
moves by 70.

Adding a plain proportional gain controller - step the current toward a target amplitude after
each burst - does not close the gap. It changed the reading from 52 to 49 against a vendor
reference of 60. Goodix's actual control law is not recoverable from a register trace, and the
difference it makes is evidently more than "keep the amplitude in range".

### What is still missing

Setting mode 5 explicitly does not reproduce the vendor's result: it yields no usable cluster
where mode 4 gives a steady 52. But one run *did* return 59, matching the vendor - the run that
followed immediately after a vendor measurement, inheriting whatever state it left behind.

That is the shape of the remaining gap. Our sequence reproduces the daemon's register writes but
not the whole device state it establishes, and both symptoms - the 13% bias and the flat second
channel - point at the same thing. Until that is understood the vendor daemon stays: it produces
readings that agree with a hand count, and ours does not.

## The driver's commands have names, and there is an interrupt after all

The daemon's own error strings name the full command set, which is larger than the seven
commands found by probing:

    GH_IOC_INIT            GH_IOC_ENABLE_POWER     GH_IOC_ENABLE_IRQ
    GH_IOC_EXIT            GH_IOC_DISABLE_POWER    GH_IOC_DISABLE_IRQ
    GH_IOC_REMOVE          gh_dev_wait_irq

Two things follow.

**`_IOW('G',2,4)` is `GH_IOC_ENABLE_POWER`/`GH_IOC_DISABLE_POWER`** — one command taking 1 or 0,
which is exactly the shape we found empirically. By the same pattern `_IOW('G',7,4)` is almost
certainly the IRQ pair, and behaves like it: see below.

**There is an interrupt path, and an earlier section of this file was wrong to say otherwise.**
That claim rested on watching `poll`, `select` and `read` on the device and seeing none of them —
but `gh_dev_wait_irq` is an *ioctl*, so no amount of watching those three would ever have found
it. An interposer only sees what it interposes.

### The interrupt is a competitor, not a helper

Enabling it makes things worse, informatively so:

| `G,7` | FIFO level after arming | data read back |
|---|---|---|
| 1 (enabled) | sticks at 2544 | all zeros |
| 0 (disabled) | 100, a plausible count | values around 3,210,565 — the PPG range |

With the interrupt on, the kernel driver services the chip and drains the FIFO before we can. So
a userspace driver wants `GH_IOC_DISABLE_IRQ` and to poll, which is the opposite of the usual
advice and the opposite of what the daemon does.

### The per-burst loop, and the interrupt wait

Logging *every* ioctl on the device - rather than a whitelist - shows what the daemon actually
does between bursts. The argument must be printed as a value and never dereferenced, because
some of these commands pass an immediate; dereferencing is what crash-looped the daemon earlier
and caused the whitelist that hid all of this.

     7.889  W dd dd c3          arm the read
     7.899  IOCTL 40184709      publish the previous result
     8.875  IOCTL 00004701      <-- blocks about a second, 35 times in one capture
     8.876  IOCTL 825a470a      read the 602-byte buffer
     8.876  R 004a -> 00c8      level, 200 samples
     8.882  R aaaa x3           drain

`_IO('G',1)` is the interrupt wait — `gh_dev_wait_irq` from the daemon's strings. This is the
mechanism an earlier section of this file wrongly said did not exist, having looked only at
`poll`, `select` and `read`. And `_IOR('G',10,602)` is read once per PPG burst, so calling it
"the accelerometer FIFO" was at best incomplete.

**The wait blocks forever if the chip is not sampling.** Always call it from a child process with
an alarm, as the command probe does. Called directly it hung for ten minutes with the sensor
powered on a wrist.

Adding both calls to our own start does **not** produce data: the wait never returns, because our
chip never raises an interrupt. So these commands are how the daemon *reads* a running sensor,
not what makes it run. After our two-pass sequence the part is awake and addressable
(`id=0031`, `0022=1a80`) but `0008` stays `0000` and no interrupt ever arrives. That is where the
remaining gap is.

### The remaining commands, probed

`nr` 0, 1, 3, 5 and 6 were probed with the chip powered and its id checked after every call.
Three are accepted and none breaks the part:

    _IO ('G',1)      ok        _IO ('G',0)  fail      _IO ('G',3)  fail
    _IOW('G',3) 1    ok        _IOW('G',0)  fail      _IO ('G',5)  fail
    _IOW('G',6) 1    ok        _IOW('G',1)  fail      _IOW('G',5)  fail

Probe them with a timeout. A first attempt called them directly and hung for ten minutes — one of
these blocks, which is what `gh_dev_wait_irq` would do — so each call belongs in a child process
with an alarm, and a blocking command is then a result rather than a hang.

Calling `_IOW('G',3)` or `_IOW('G',6)` before the start sequence does **not** make sampling
stream. Runs with each, and without either, produce the same output.

### What the FIFO actually returns, and a correction

It is tempting to read the first value of each burst as a sample: it lands around 3,210,5xx,
which is exactly the range of genuine PPG. It is not a waveform. Across runs it reads 3210514,
3210527, 3210529, 3210559 — drifting slowly upward and never oscillating, which is an ambient DC
level in a latched register. A pulse moves by tens of counts within a second. Everything after
that first pair is around 11.5 million, well outside the range the daemon's own captures show.

So standalone sampling is **not** working, and an earlier note here claiming real samples was
reading a static register. What is solid is everything up to that point: power, register access,
the two-pass configuration, and the arm — all with no vendor daemon running.

## The start is two passes, and one command was missing

Replaying the daemon's writes as a single script never sustains sampling. The reason is visible
once the whole run is laid out rather than the block nearest the first FIFO read: **the daemon
configures the chip twice, with different values for the same registers, and commits the first
configuration with a command we had never sent.**

    ...first configuration...
    W 0002 fe30
    W dddd c1          <- commit. Not c0, not a1. This was the missing command.
    W dddd c0
    R 0008 -> 0010     status check
    R 00c0 -> 0001
    W dddd c4 / c0     sleep, wake
    ...second configuration, different values...
    W 0044 00c8        FIFO watermark, 200 samples
    W 0002 fe2e        enable
    W dddd a1          arm -> sampling starts

So the `0xdddd` command set is: `c0` wake, `c4` sleep, `c1` commit a configuration, `a1` arm the
sample stream, `c3` arm a FIFO read.

### Which values come from tables, and which are computed

Searching the binary for each register/value pair separates the two cleanly. The configuration
values are all in the tables beside the ones already documented — the first pass uses one set and
the second another:

    0x25aa6:  0016=0147  0080=0605  0082=01c6  0084=0023  0118=9055  0136=0000  0186=0406
    0x25c3c:  0016=00a3  0080=0605  0082=01c6  0084=0121  0118=1f69  0136=00a0  0186=1807

Exactly two values in the entire sequence appear in **no** table, so these are the ones the
daemon computes at runtime:

- **`0x0044` = 200** — the FIFO watermark, and `0x004a` reports the same 200 back.
- **`0x0002`** — the enable: `0xfe30` for the first pass, `0xfe2e` for the second.

Neither appears as an immediate in the code either: a Ghidra pass over all 657 functions found no
literal `0xfe2e` or `0xfe30` anywhere, which is what says they are computed rather than stored.

### Where this currently stands

`tools/gh3011/ppg.c -self` implements the two-pass sequence. With the daemon stopped it powers
the part, reads the id, and completes the first pass correctly — `0x00c0` reads back `0001`,
matching the daemon's own trace at the same point. After the second pass the chip stops
answering: `0x0022` reads `0000` and the FIFO level stays 0.

So the remaining gap is narrow and well-located: something between committing the first
configuration and arming the second. The likely candidates are the two computed values, since
they are the only parts not taken verbatim from a table, and the status reads the daemon makes
between the passes (`R 0008 -> 0010`) suggest it waits for a state rather than proceeding blind.

## Configuration tables

The daemon holds Goodix's HBD library statically and its callback table is readable as strings at
0x258a3: `HBD_RET_OK`, `gh30x_hb_start`, `gh30x_Load_new_config`, `i2c_write`, `i2c_read`,
`notifyResultData`, `Deviceopen`, `Devicedisable`.

Tables of `{u16 reg, u16 val}` pairs sit at file offsets 0x25aa6 (48 pairs), 0x2593c (34),
0x25be4 (35) and 0x259c8 (14). The registers they name overlap the ones the tap shows the daemon
touching — 0x0080, 0x0082, 0x0084, 0x0118, 0x0136, 0x0186 — which is good corroboration that they
are configuration. Their *values* have not been independently confirmed; the read-backs that
appeared to confirm them do not reproduce.

## Things that looked true and were not

Recorded because each cost hours and each is easy to arrive at again.

- **"The daemon fetches the waveform over the i2c passthrough."** Stated as the central fact in
  an earlier version of this file. It does not: it makes 34 transactions at startup and none
  during a measurement.
- **"Our i2c reads are reaching the part, because configuration values read back unchanged."**
  Those read-backs do not reproduce. The chip id register reads zero from our code and `0x0031`
  from the daemon's.
- **"0x0086 and 0x008a are the PPG channels."** They were 24-bit-looking values in a sweep that
  is now known to return block-constant junk. There is no evidence for them.
- **"There is no FIFO command."** There is; the scan tried ten round sizes and the real one is
  602 bytes.
- **"`_IOWR('G',8,4)` overflows the caller."** It does not. Given a large buffer it writes
  exactly four bytes and returns the current mode; the fault was a stack variable in the test.
- **"`G,10` is the PPG FIFO."** It is the accelerometer, by magnitude and by the kernel handler.
- **"The chip returns zeros, so the protocol is wrong."** Partly: the chip also has to be
  running, and only the sensor framework starts it. The absent LED was the tell, and it was
  mentioned before it was believed.
- **"`/dev/socket/gh30x_socket` is the daemon's output."** Nothing ever listens on it:
  `/proc/net/unix` shows it without `SO_ACCEPTCON`. But init does create it and hand it to the
  daemon, and a hand-started daemon without it never receives a start request.

## Practical notes

- Ghidra loads `gh3011_service` at base **0x10000**; its `FUN_000xxxxx` addresses are that much
  above the file offsets. Several hours went into disassembling the wrong regions.
- objdump does not resolve this binary's Thumb-to-ARM PLT veneers, so `blx ... <ioctl@plt>` never
  appears and grep finds no callers. Ghidra does resolve them.
- The daemon exits immediately and silently if started without `--daemon`.
- No measurement completes with the watch off the wrist: the LED lights, but 36 seconds of
  `/dev/input/event1` produced zero events. Check this before concluding a start sequence failed.
- **Anything that starts the chip must stop it on every exit path**, including signals: a test
  killed by a harness timeout left the sensor lit on a wrist for eight minutes. An `alarm()`
  inside the program, handlers for TERM/INT/SEGV/ALRM, and `atexit` are the minimum. Note that a
  bare `alarm()` with no handler kills the process before it can print anything — which also
  makes an empty log look like an empty device.
- Stopping the daemon for an experiment is `setprop ctl.stop gh3011_daemon`, and it must be
  restarted by the shell around the test so it happens even if the test dies.
